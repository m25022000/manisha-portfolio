Actual Artifact

CI/CD Pipeline Security Research Report

Research Question

How can organizations protect CI/CD pipelines from credential theft, supply-chain compromise, unauthorized changes, insecure dependencies, and undetected malicious activity?

Executive Summary

A CI/CD pipeline should be treated as a production security boundary rather than only as a tool for automating software delivery. Pipelines interact with source repositories, build workers, package registries, secrets, cloud accounts, and production systems. A weakness in one stage can allow an attacker to modify code, steal credentials, replace artifacts, or deploy unauthorized changes.

A secure approach uses layered controls: least-privilege identities, protected branches, ephemeral build environments, dependency scanning, secret detection, artifact signing, approval gates, deployment restrictions, and centralized logging. Security checks should be integrated throughout the delivery lifecycle instead of being postponed until after deployment.

Identity & Secrets

Use short-lived credentials, dedicated service accounts, role separation, secret managers, and minimum necessary permissions.

Supply-Chain Integrity

Pin trusted dependencies, scan components, generate an SBOM, sign artifacts, and verify provenance before deployment.

Visibility & Response

Centralize pipeline logs, alert on abnormal activity, preserve evidence, and define incident-response procedures for pipeline compromise.

Critical AI Evaluation

What the AI Did Well

STORM organized the research into multiple expert viewpoints and correctly emphasized secrets management, least privilege, software-composition analysis, SBOMs, artifact signing, security testing, and isolated build environments.

Its strongest insight was treating the pipeline itself as an attack surface—not merely the application code that the pipeline delivers.

Human Validation

What Needed Improvement

The initial output did not go far enough into runtime monitoring, incident response, post-compromise investigation, or the operational steps needed when suspicious pipeline activity is detected.

I added centralized logging, alerting, evidence retention, response procedures, and a threat-to-control analysis so the artifact would be more useful to practitioners.

Practitioner Checklist

✓Protect branches and require reviewed pull requests.
✓Remove hardcoded secrets and use managed secret storage.
✓Use short-lived, least-privilege pipeline identities.
✓Scan source code, dependencies, containers, and infrastructure code.
✓Generate an SBOM and record build provenance.
✓Sign and verify release artifacts before deployment.
✓Isolate build runners and avoid long-lived shared environments.
✓Centralize logs and alert on unusual pipeline behavior.
✓Use approval gates for sensitive production deployments.
✓Test incident-response procedures for pipeline compromise.
